每个数字后面注明出处（论文页码/表号、仓库文件、或本文 §10 的命令）。

> **一句话结论**：PureDocBench 的"仿真"不是从原始文本进化出来的，而是**一次性让 LLM 把整页 HTML/CSS（内容、版式、样式）写出来，
> 人工筛掉坏页，浏览器渲染成图，再从同一份 HTML 抽标注**。它的科学贡献在**图像层与评测层**（对齐三视图、源可追溯标注、58 模型榜单），
> 不在内容层——内容层没有任何一步对着真实文档做分布校准，提示词也没有公开。
> 本仓已经照它做完了图像层（degrade.md）；**它没做、别人也没串起来的，是值层机理 + 语义真值 + 多源档案 + 闭环评测**。
> mirobody-gen + mirobody 能成高水平论文，但定位必须是"闭环"，不能写成"医疗版 PureDocBench"。

## 0. 先回答提出的问题

| 问题 | 短答 | 详见 |
|---|---|---|
| 它怎么从原始文本进化到足够仿真的报告？ | 没有"进化"过程。五步流水线里只有一步产生内容（LLM 一次性写整页 HTML/CSS），仿真度来自 LLM 对该类文档的先验 + HTML/CSS 作为可执行中间表示 + 人工拒绝采样。没有真实感度量，没有对真实语料的校准 | §2 |
| 有没有与 mirobody-gen 类似的工作？ | 分层看都有邻居：图像层（它自己、WeVisDoc、Real5-OmniDocBench、DocPTBench、MDPBench）、值层（Synthea、ESL-Bench、Synthetic Hospital）、"合成医疗文档 + 劣化 + 抽取"（Yu 等 medRxiv 2026，1,000 份基因报告、7 个模板）。**把机理虚拟人 → 多源档案 → 对齐劣化 → 语义真值 → 评测标准化系统串成闭环的，一个都没有** | §7 |

| 这个工作值不值得发更高的论文？ | 它已经在冲顶会；作为"又一个劣化基准"，上限就是数据集与基准类论文（Datasets & Benchmarks 赛道），再往上需要方法贡献 | §5 |

## 2. 数据构造流水线：一步一步拆

### 2.1 五步里谁在做事

论文 §2.1 与图 2 给的是五步（0–4）。按"这一步是 LLM、人、还是确定性程序"拆开，是理解"仿真从哪来"的关键：

| 步 | 做什么 | 执行者 | 输入 → 输出 | 备注 |
|---|---|---|---|---|
| 0 | 元提示设计：按 66 个子类写提示，指定文档类型、版式、领域、语言、元素构成（几个公式、几张表、有无代码/图） | 人 | 子类 → 提示词 | 图 2 的例子："英文笔记本风格研究海报 · FoldFlow 蛋白骨架生成 · 方法/流水线/算法/结果/消融/贡献/阅读清单 · 3 公式 2 表 · 双栏网格 · 彩色卡片 · 右侧公式编号" |
| 1 | LLM 一次性输出**自包含**的 HTML/CSS：正文、结构化表格、LaTeX 公式、样式全在一页里 | **Claude / ChatGPT** | 提示词 → HTML | 内容是 LLM 编的（人名、医院名、数值、诊断）；版式也是 LLM 编的（grid、配色、字体） |
| 1' | 人工筛选：拒绝"版式塌掉"与"内容重复"的页 | 人 | HTML → 保留的 HTML | 这是唯一的质量闸门，标准只有两条：layout integrity、content diversity |
| 2a | 浏览器渲染高分辨率 PNG（仓库脚本用 Playwright Chromium，`--dpi 300`；样页 3600×4470 px） | 程序 | HTML → Clean 图 | 确定性 |
| 2a' | 数字劣化（10 场景）与真实采集（4 链路） | 程序 / 人手拍 | Clean → Digital / Real | §3 |
| 2b | **LLM 辅助**从同一份 HTML 抽 OmniDocBench 格式标注：文本、表格 HTML、公式 LaTeX、阅读顺序 | LLM + 程序 | HTML → GT JSON | 注意措辞是 "LLM-assisted extraction reads the same HTML"，不是从 DOM 确定性编译 |
| 3 | 校验：schema 与源检查（文本匹配、标题、LaTeX、路径、ID）+ 多轮人工交叉复核（渲染页 ↔ GT） | 程序 + 人 | GT → 验证过的 GT | 数据卡列了 7 项 1,475/1,475 的自动检查 |
| 4 | 配对基准 | — | 1,475 × 3 | 三视图共用一份 GT |

### 2.2 "仿真"从哪里来，缺什么

从上表看，仿真度只有三个来源：

1. **LLM 对该类文档的先验**——它见过很多真实的检验报告、发票、判决书，所以能写出"像"的页面；
2. **HTML/CSS 作为可执行中间表示**——一次编译出像素级精确的图，一次遍历出标注（WeVisDoc §3.2.3 把这叫"语义 HTML 双编译"，本仓 `document.py → pdf.py` 是同一结构）；
3. **人工拒绝采样**——但只筛"塌没塌、重不重复"，不筛"像不像真的"。

论文里**没有**的东西，每一条都是本仓已经有或必须有的：

| 缺项 | PureDocBench 的做法 | 后果 | 本仓对应 |
|---|---|---|---|
| 真实感度量 | 无。数据卡自己写"文档风格可能反映提示设计、渲染引擎、字体与生成模板" | 无法回答"比真实报告难还是易" | `audit/fidelity.py`：指纹种数比、单位陷阱文档率、参考范围写法 JS 散度，两边同一函数 |
| 内容与值的来源 | LLM 编 | 单页内部可以自洽（§2.3 实测），但跨页无纵向、无人群分布、无诊断约束 | 机理模型 + 恒等式 + WS/T 参考区间 + 生物学变异；`audit/clinical.py` |
| 版式多样性的来源 | 每个子类一个提示，LLM 随机性 | 66 个子类 × 20 页左右，风格趋同（样页整齐得像教科书） | 从 627 份真实文档蒸馏的 20 种列组、65 种参考值方言、机构过程长尾（NUMBERS.md） |
| 提取陷阱 | 无此概念 | 只能测"认没认出字"，不能测"认出来之后读不读得对" | 62 类陷阱、逐行归因、最小对照对（PAPER.md C2/C4） |
| 语义真值 | 无。GT 是"纸上印了什么"（页面级 Markdown / 表格 HTML） | 不能考术语层（LOINC）、不能考弃权 | 两层真值：印刷真值 + 语义真值（指标、LOINC、数值、UCUM、日期） |
| 提示词发布 | 未发布 | "生成工具可复用于新领域"的主张不可复现 | 本仓 `spec/` 全部入库 |

### 2.3 医疗样页实测：LLM 一次性生成的报告到底什么样

看的是 `06_medical/01_medical_report/medical_report_001`（仓库 `assets/samples/06_medical.png` 就是这张；GT 文本从 review 数据里取，§15 命令 ②）。

**页面构成**：市第一人民医院 · 检验科 → 报告单号/条形码 → "生化全套检验报告" → 患者信息（姓名、性别/年龄、身份证号、科室/病房、医嘱医生、医疗卡号、住院号、临床诊断"代谢综合征"）→ 标本信息 → 一张 7 列大表（项目 / 缩写 / 结果 / 单位 / 参考范围 / 异常）分 6 个分组（肝功能 11 行、肾功能 4 行、血脂 7 行、血糖 2 行、电解质 6 行、心肌酶 5 行）→ 质控信息（仪器 Siemens ADVIA 2400、质控批号、试剂批号）→ 临床参考意见（一段话）→ 重要说明 → 三个签名栏 → 页脚。中英双语表头、异常值红/蓝底、↑↓ 箭头。

**值的内部一致性**（手算）：总胆红素 18 = 直接 4 + 间接 14 ✓；总蛋白 72 = 白蛋白 44 + 球蛋白 28 ✓；A/G 1.57 = 44/28 ✓；Friedewald 估算 LDL = 6.82 − 0.96 − 3.28/2.2 = 4.37，印的是 4.28（直接测定法允许的偏差）；肝酶、肾功能、血脂、血糖/HbA1c 的异常方向与"代谢综合征"诊断和结尾那段临床意见互相解释得通。**结论：单页内 LLM 是能写出自洽的检验报告的**——所以"LLM 写值不靠谱"不能作为我们的论据；我们的论据是**纵向**（同一人多年）、**人群**（患病率与分布）、**跨文档**（体检报告上的体重与体重秤序列同源）与**可审计**（恒等式是程序保证的，不是碰巧成立的）。

**它"太完整"的地方**（与 NUMBERS.md 的真实统计对照）：

| 现象 | 样页 | 真实语料（627 份） |
|---|---|---|
| 参考范围 | 每一行都有，写法统一（`7-56`、`<5.18`、`>1.04`） | 9 种方言，包括分性别/分行/带文字的；`unit.missing` 类陷阱文档率 9.6% |
| 单位位置 | 独立一列 | 独立列 243 / 无 135 / 在参考范围里 86 / 粘在值里 64 / 在表头 7 |
| 表格 | 一张规整大表，列头齐全 | 22.6% 的文档**没有表格**（纯叙述型）；列组 20 种角色组合 |
| 陷阱 | 一处：AST 在肝功能与心肌酶两组各印一次（同值）——这在真实报告里确实常见 | 每文档陷阱 p50=4 / p95=8 |
| 版式 | 一页一个模板，无机构方言 | 74.6% 的文档版式指纹只出现一次 |
| 元信息 | 身份证号打码、电话 `0571-XXXX-XXXX` | — |

医疗域 200 页的构成（review 数据）：10 个子类各 20 页：medical_report、prescription、clinical_record、medical_bill、health_record、medical_certificate、imaging_report、surgical_record、discharge_summary、drug_instruction。`health_record_001` 是一本儿童预防接种证（三张表：一类疫苗、二类疫苗、待接种计划），说明"health_record"在它这里是**广义健康记录**，不是我们说的体检报告书。**与 mirobody 最相关的只有 medical_report（20 页）与 discharge_summary、clinical_record 里的化验片段**。

### 2.4 标注质量：它自己的 review 数据怎么说

review 数据的 meta：88,636 条标注，其中 `items_with_bbox` 88,389、`items_unmatched` 247、`items_low_similarity` 2,009——即 **2.5% 的标注在它自己的复核工具里与渲染页匹配度低或找不到**。医疗域 200 页里 unmatched 12（出院小结 8、药品说明书 4）、low_similarity 4。这不算差，但说明"源可追溯"不等于"零误差"：因为标注是 LLM 辅助抽的，不是从 DOM 编译的。WeVisDoc 的双编译是纯程序的，本仓也是（`generator/document.py` 的印刷真值直接来自排版数据结构，`audit/readability.py` 再核对纸上确实印了）。

它把标注错误当成运营问题处理：静态 review app、拖框修正、导出 patch JSON、issue 模板、版本化 GT（`gt/latest.json` 记录精确版本、`changed_cases.json` 记录改动）。这套流程值得原样借（§8.3）。

### 2.5 阅读顺序、公式、代码

标注类型计数（review meta）：text_block 65,483、title 14,234、table 3,804、header 1,895、equation_isolated 811、footer 683、reference 561、table_caption 414、figure_caption 313、page_number 257、code_txt 142、figure 39。医疗页几乎没有公式，所以医疗域的 Formula CDM 是在极少样本上算的，看医疗分要主要看 Text Edit 与 Table TEDS。

## 3. 三视图与劣化：本仓已经照抄的部分，和还没抄的部分

### 3.1 Digital 轨：10 场景

发布的数字轨 `degraded_v2_merged/`：每个 Clean 页 round-robin 分到 10 个场景之一（每场景 147–148 页），severity 统一 `moderate = 0.6`，每张图带参数 JSON，`scene_mapping.json` 记录来源（附录 F）。10 个场景：`aged_archive`、`book_binding`、`multi_gen_copy`、`fax_thermal`、`low_quality_print`、`ink_bleed`、`heavy_compression`、`uneven_lighting`、`geometric_distort`、`noise_blur_combo`。算子是 OpenCV/NumPy 的低层操作（纸纹、泛黄、霉斑、褪色、页曲、装订阴影、透印、复印对比、滚筒条纹、热敏二值化、打印条带、墨水扩散、JPEG、降升采样、光照梯度、暗角、透视、镜头畸变、旋转、高斯噪声、运动模糊、色温）。

另有一个**消融生成器**（未用于主榜单）：15 个算子按 Print → Paper → Capture → Digital 四阶段组合，图 18 给了 s=0.7 与 s=1.0 的具体参数（例如 JPEG 质量 42 / 30，透视位移 3.1% / 4.0%，倾斜 ±3.1° / ±4.0°，高斯噪声 σ 14 / 20），图 19 给了另一套 10 个"采集场景"（flatbed_scan、archival_scan、bound_manual_scan、office_copy_scan、harsh_photocopy、mobile_capture、glossy_phone_capture、low_light_phone、folded_receipt_capture、thermal_receipt_capture）及各自强度区间与前三算子权重。**注意论文里同时存在两套场景命名**（发布轨的 10 个与消融器的 10 个不是同一套），读代码时别混。

### 3.2 Real 轨：4 链路，每页只配一条

4 条链路：手机拍打印件、手机拍复印件、手机拍屏幕、截图 + 社交软件转发压缩。子条件编码在文件名 `__real_` 之后：来源（phone/screen/screenshot）、纸张状态（flat/creased/bent/cover/photocopy）、光照（normal/low-light/flash/shadow/outdoor/screen）、几何（top-down/oblique/handheld/screenshot）。**每页只有一张 Real 图**（4,425 = 1,475 × 3），所以 Real 分数把"链路难度"与"页面难度"混在一起；66 页样本清单里的链路分布：手机拍平整纸俯拍 21、折痕 9、拍屏 8、拍复印件 6、截图 5、弯折 5、隔套 5、暗光 3、斜拍 3、闪光灯 1（本仓 `SCENE_WEIGHTS` 目前按这个量级配，degrade.md §3）。

**可读性问题**：人工复核发现 83 张 Real 图（5.63%）文字无法可靠核对，主要是长页整页重拍后细节丢失（附录 C，图 16）。剔除后 51 个模型的 Real 分平均涨 2.32、Avg₃ 涨 0.77，排名 Spearman ρ = 0.998，前十不变。他们的结论是"绝对分被压低、相对排名稳定"，并提出未来采集要记录质量标志。**这是我们要提前避开的坑**：本仓 `finger_occluder` 只压页边留白、严重档进 `stress` 不进主榜、`readability --ocr` 按场景报告——三条都是构造性地保证"真值确实可见"，比事后审计强。

### 3.3 "劣化只改像素，不改内容"

三视图共用一份 GT 是整个基准的立足点。WeVisDoc 把它说得更严："变换后的视图只有在所有被监督内容仍可见可读时才保留原目标；丢内容的视图要么拒绝，要么改成可见内容的裁剪目标"。本仓 degrade.md §7 的对齐视图（`view:<场景>`）与 `pairs.jsonl` 就是这个原则的实现，且判定放在语义层。

### 3.4 与本仓 degrade.md 的差异清单

| 项 | PureDocBench | 本仓 |
|---|---|---|
| 场景 | 10 数字 + 4 真实链路（手拍） | 24 个场景，全部程序生成（T2 扫描 5 / T3 手机 10 / T4 劣化 6 / T6 屏幕 3），无真实手拍轨 |
| 参数来源 | 设计者定，severity 三档 | 对着真实语料 315 张图的聚合统计校准（`docs/numbers_images.json`：白底 51%、灰度 42%、JPEG 质量中位 93、几乎不歪、横版 45%） |
| 国内链路 | 无 | `app_enhance`（扫描全能王/微信文档模式）、`wechat_scale`（1280 规则）、`phone_frame`/`desktop_frame`、`rotate_quarter` |
| 内容遮挡 | 事后审计，83 张不可读 | 手指只压页边留白；严重档进 stress |
| 依赖 | OpenCV | PIL + numpy |
| 真值粒度 | 页面级 Markdown / 表格 HTML | 逐行印刷真值 + 语义真值 + 块真值 |
| 缺的 | — | **没有真实手拍轨**。这是我们相对它唯一的硬缺口；补法见 §9 第 3 条 |

## 4. 评测与主要结果

**指标**（§3.1，沿用 OmniDocBench）：TextEdit↓（页面级归一化编辑距离）、FormulaCDM↑、TableTEDS↑、ReadOrderEdit↓（单独报）。
`Overall = [100(1 − TextEdit) + FormulaCDM + TableTEDS] / 3`；`Avg₃` = 三轨 Overall 均值。

**58 模型**：13 流水线式专用（PaddleOCR-VL-1.6、MinerU2.5-Pro、TeleOCR…）、19 端到端专用（OvisOCR2、WeVisDoc-2B/4B、HunyuanOCR-1.5、DeepSeek-OCR-2…）、26 通用 VLM（Qwen3.5/3.6/3.8 全系、GLM-5.3-Flash、Gemini 3.6 Flash、Claude Opus 5、GPT-5.6 Sol、Kimi K2.6…），发布时间截至 2026-09。

**四条发现**（§3.2–3.3，表 2 与图 3、4）：

1. 没解决：最好 Avg₃ 79.69（GLM-5.3-Flash），均值 63.84，中位 66.20，最好最差差 50.2 分；只有 7 个模型过 75。
2. 小专用模型能打：MinerU2.5-Pro（1.2B）70.07 ≈ Kimi K2.6（1T/32B 激活）70.10；WeVisDoc-4B 75.57 > Qwen3.5-122B-A10B 74.11。
3. 劣化改变排名：Clean→Digital 平均掉 3.34，Clean→Real 掉 11.61；流水线专用掉 5.17 / 14.23，端到端专用 4.14 / 12.99，通用 VLM 只掉 1.84 / 9.30。TeleOCR Clean 第一（87.16）但 Real 掉 18.08；Gemini 3.6 Flash 从 Clean 第 6 升到 Real 第 1（75.73）；Claude Opus 5 Digital 反而掉 10.05（比 Real 掉得多，异常点）。
4. 组件各有所长：端到端专用文本与阅读顺序最好，通用 VLM 公式与表格最好；GLM-5.3-Flash 总分第一但阅读顺序比 TeleOCR 差 14.77 分。

## 5. 发表水平评估

### 5.1 强在哪

* **规模与新鲜度**：58 个模型、覆盖到 2026-09 的发布，绝大多数基准论文做不到；榜单还在持续更新（09-21、09-26 两次）。
* **溯源**：HTML 源、GT、三视图、每张劣化图的参数 JSON、场景映射、GT 版本别名、Croissant 元数据、SHA256 分卷校验——工程上非常完整。
* **自我审计**：附录 C 主动量化了 Real 轨的不可读比例并做敏感性分析；附录 A 对 30 个相关基准逐个核对版本与口径（表 1 的脚注写明"符号只概括范围，不代表指标质量"）。这是审稿人喜欢的诚实。
* **配对设计**：三视图共用 GT 使"采集链路的代价"成为可直接相减的量，这一点 DocPTBench（只 100 页有物理版）、Real5-OmniDocBench（继承 GT）都不如它干净。
* **发现有信息量**："小专用模型 ≈ 大通用模型"、"劣化改变排名"、"组件各有所长"都是可指导选型的结论。

### 5.2 弱在哪

* **内容层是黑箱**：提示词未发布；"人工筛选"只有两条标准；没有任何真实感度量；数据卡自己承认风格可能反映提示与渲染引擎。"用生成内容降低训练数据重叠风险"是对的，但代价是"LLM 风格的文档"这一新的偏差没有被量化。
* **"源可追溯"打了折扣**：标注是 LLM 辅助抽取 + 人工复核，不是 DOM 编译；自己的 review 数据里 2.5% 标注匹配度低。
* **指标沿用**：OmniDocBench 的编辑距离对"语义遗漏"（漏一个 25% 的权重标签）与"结构一致性"不敏感，论文自己列为局限 (i)。
* **Real 轨设计**：每页一条链路、四链路份额不均、5.63% 不可读；"outdoor""shadow"等子条件出现在文件名规范里但样本清单里几乎没有。
* **两套场景命名并存**（§3.1），读者容易混淆。
* **v1 的攻击性主张撤回**：说明 v1 的 OmniDocBench 审计经不起推敲或不便发表；对我们的启示是，**不要把"对手基准有错"当成自己的贡献**（PAPER.md §0 已经在 MedRepBench 上吸取了同样的教训：只报口径问题，不报"他们错了"）。

### 5.3 采用情况

WeVisDoc（腾讯微信视觉，arXiv:2609.20423，2026-09）把 PureDocBench 当主评测之一，报告 4B 模型三轨均分 75.54，并把结果提交进榜单；NaviDC-OCR 在自己仓库里自报 PureDocBench 成绩。发布四个月即有第三方模型论文把它当靶子，这对基准来说是最重要的采用信号。

### 5.4 场地推断

v2 正文 9 页 + AI Use / Ethics / Reproducibility 三段声明 + 2026-09-27 上传，而 ICLR 2027 正文截稿是 2026-09-25（AoE）。**形态与 ICLR 2027 投稿一致**（推断，未核实 OpenReview）。作为数据集与基准论文，它的天花板是 ICLR/NeurIPS 主会或 NeurIPS D&B 赛道；再往上（方法贡献）它没有——它不提出模型，也不提出新指标。

### 5.5 发表去向与被引用（截至 2026-09-29）

* **论文本身**：仍是 arXiv 预印本（v2），没有会议或期刊版本；Semantic Scholar 记录引用 4 次（其中 2 次"有影响"）。发布不到五个月，这个数字不说明问题，下面的采用情况才说明问题。
* **谁把它当靶子**（arXiv API 按标题/摘要检索 `PureDocBench`，4 篇，全部在摘要里报它的分数）：

| 论文 | 类型 | 怎么用它 |
|---|---|---|
| TeleOCR（arXiv:2608.12898 v3，2026-08） | 模型技术报告 | 摘要报 OmniDocBench v1.6 96.87、Wild-OmniDocBench 88.53、PureDocBench 78.41；ICDAR 2026 Sci-ImageMiner 挑战赛第一 |

## 6. 与 mirobody-gen 逐项对照

| 维度 | PureDocBench | mirobody-gen（2026-09-29 状态） |
|---|---|---|
| 目的 | 评测通用文档解析模型（OCR 层） | 评测 mirobody 的健康档案标准化（提取 → 解析 → 编码 → agent 四层） |
| 领域 | 10 领域 66 子类；医疗 200 页里检验报告 20 页 | 只做健康档案；体检报告书、化验单、门诊病历、心电图、超声、居家记录、导出表、设备批次、日记、基因导出文件 |
| 内容来源 | LLM 一次性编 | 队列引擎（8 原型、6 干预剧本、5 随机事件、16 套医嘱、三档套餐）+ 机理取值 + 恒等式派生 + 黏性所见按年推进 |
| 纵向 | 无，页与页无关 | 60 人 546 次就诊，同一人多年；体重秤序列与体检体重同源；血压计与门诊血压同源 |
| 多源 | 单一模态：页面图像 | 文档 + 设备批次（133,294 条）+ 日记（2,403 句）+ 基因文件（26 份，5 种厂商格式）+ 主诉（278 条，对照 ICPC-3） |
| 真值 | 印刷层：文本/表格 HTML/公式/阅读顺序 | 两层：印刷真值（MedRepBench 五字段）+ 语义真值（指标、LOINC、数值、UCUM、日期）+ 块真值（键值对、总检、主诉、诊断）+ 逐行陷阱名 + 必须弃权行 |
| 版式多样性 | 每子类一个提示，LLM 随机性 | 从 627 份真实文档蒸馏的 spec（列组、参考值方言、单位位置、标记）+ 机构过程（两个大客户 + 长尾 + 个人粘性 + 逐年改版） |
| 提取陷阱 | 无此概念 | 62 类、文本层可造 46 类、逐行归因、最小对照对 |
| 图像层 | 10 数字场景 + 4 真实链路（手拍） | 24 场景，参数按真实语料校准；**无真实手拍轨** |
| 真实感度量 | 无 | `audit/fidelity.py`（两边同一指纹函数） |
| 临床/值审计 | 无 | `audit/clinical.py`：12 条恒等式、硬边界、人口学、标记一致、RCV、诊断—值互证 |
| 隐私 | 内容为虚构，无真实来源 | 结构论证：真实记录不在取值路径上；三道闸门（回放检测、PII 谓词、白名单） |
| 可再生 | 固定 1,475 页；"新提示可扩展"但提示未公开 | 生成器 + seed，同 seed 逐字节一致；换 seed 得未见过的一批 |
| 评测对象 | 58 个公开模型 | 一个产线（mirobody）+ 可选的公开模型面板；**闭环**：合成 → 劣化 → 抽取 → 标准化 → 与语义真值比 → 回到生成器补陷阱 |
| 规模 | 4,425 图 | 726 份文件（381 份走 OCR 路径）+ 447 份对照对；随时可扩 |
| 运营 | 榜单、review app、GT 版本、社区提交 | 无 |

**一句话**：PureDocBench 是"横向宽、纵向浅"的 OCR 层基准；mirobody-gen 是"横向窄、纵向深"的语义层闭环。两者在图像层重合（本仓已抄），在其它层互补。

| **Yu 等，medRxiv 2026**（"Benchmarking LLM-based IE Tools for Medical Documents"） | 合成医疗文档 + 劣化 + 抽取 | 1,000 份合成基因检测报告、JSON 参考、干净/传真两版 PDF、传真劣化使 F1 降 38.8% | 7 个模板、无纵向、无人群、无标准化、无真实感对账。**这是最接近的一篇，也是最小的一篇** |

| **Synthetic Hospital**（CMU，Park/Chen/Dettmers，2026-09-24；精读见 §12） | 值层 | 从 7,003 道 USMLE 式题拼出 1,268 名纵向患者 / 5,602 次就诊；标签先于叙事、由本体图确定性导出；医生盲判 53%；FHIR R4 + 13 工具的模拟 EHR；held-out 标签只在评分器里 | **没有文档/图像，明确不模拟缺失、矛盾与文档错误，化验只有 3,488 条所见且 LOINC 覆盖 28.9%**。与 ESL-Bench 同赛道；相关工作里放"值层"，正面对比三点（§12.4） |
| Improving the Realism of Synthetic Clinical Benchmarks（2026-08） | 值层 | 把"真实感提升"形式化为效用约束下的优化，量缺失结构/简单度/结构合理性/人群对齐 | 只针对 Synthea 派生的结构化表；无文档。它的"真实感 ≠ 效用"框架可以引用来支撑 E1 |
| Synthea / PySynthea / Coogee | 值层 | 状态机病程、FHIR；Coogee 有 LLM 一致性审计 | 无文档；观测层精度问题（issue #113） |
| SynthDocBench（2026）/ CoSyn-400K | 合成文档 | 受控 HTML 长文档 + 图表数据 QA；代码渲染的训练数据 | 通用领域；QA 不是抽取；无劣化配对 |
| Genalog / Augraphy / DocDjinn / Doc3D | 劣化工程 | 算子目录、几何、手写 | 工具，不是基准 |
| PIGEON（2026） | FHIR → 出院信 | 从 FHIR 后端生成有监督训练文本 | 文本不是图像；训练不是评测 |
| DTBench / ExtractBench / LLMStructBench | 通用抽取 | 难度轴可控、schema 抽取 | 无医疗语义、无纵向 |

**结论**：每一层都有邻居，**整条链没有人串起来**。最接近的三篇——PureDocBench（图像层结构）、Yu 等（医疗 + 劣化 + 抽取）、Synthetic Hospital（值层 + 本体落地）——各占一环。写论文时相关工作要按"层"组织，逐层说"我们与它同构、多了什么"，而不是宣称"首个"。

## 8. 对 mirobody-gen 论文的建议

### 8.1 定位：闭环，不是"医疗版 PureDocBench"

PAPER.md 的主线（C1 文档边界代价 Δ 及其三段分解）仍然成立，PureDocBench 反而给它添了一块砖：**Δ 的抽取损失那一段，可以用 PureDocBench 的口径与它的 58 模型榜单对齐**（我们的 T0→T2/T3/T6 就是它的 Clean→Digital/Real）。三条别人没有的主张：

1. **语义真值下的闭环**：同一批合成档案既能评"认没认出字"（PureDocBench 口径），又能评"读出来之后落没落到 LOINC/ICPC-3、该弃权时弃没弃权"（本仓口径），并且评完把失败簇回灌到生成器（WeVisDoc 的探针思想搬到评测侧）。
2. **多源同源**：文档、设备、基因、日记来自同一条生理轨迹，所以能考"跨源一致性"（体检报告体重 vs 体重秤、门诊血压 vs 血压计、化验血糖 vs 日记里的口述）——没有任何现有基准能出这类题。
3. **因果归因**：最小对照对 + 逐行陷阱名，把"哪一类版式现象吃掉几个点"做成配对估计；PureDocBench 只能说"Real 比 Clean 掉 11.61"，说不出为什么。

### 8.2 必须补的实验

| 实验 | 为什么 | 状态 |
|---|---|---|
| E2 排序一致性：mirobody 产线 + 若干公开模型，在 MedRepBench（真实）、本仓（合成）、**PureDocBench 06_medical（合成、第三方）** 三个集合上同口径跑 | Gill 等证明 LLM 生成的评测集常更容易且不保排序；用两个外部锚点比一个有说服力得多 | 工具就绪，未跑 |
| E3 陷阱因果效应：真实系统上跑对照对 | 规则基线不是证据 | 未跑 |
| E4 文档边界代价：ESL-Bench 用户 → 渲染 → mirobody 入库 → 原查询 | 论文主线 | 适配器未写 |
| **E8（新）图像层代价的外部校准**：把 mirobody 的 OCR 层单独拿出来，在 PureDocBench 医疗 200 页三轨上按它的公式打分，与榜单对照 | 回答"我们的 24 个场景比它的难还是易"；它的 GT 是页面级，我们评行——需要一个"页面级 → 行级"的视图转换，或只用它测 OCR 层 | 未开始 |
| 真实感度量的对照：报告 fidelity 指标时，把 PureDocBench 医疗页也过一遍同一指纹函数 | 量化"LLM 一次性生成的页有多趋同"，这是我们相对它的差异化证据 | 未开始，半天 |

### 8.3 可以直接借的工程

* **GT 运营**：静态 review app + 拖框修正 + patch JSON schema + issue 模板 + `gt/latest.json` 版本别名 + `changed_cases.json`。本仓 `harness/review/` 只有人工校样，没有修正回流与版本化。
* **敏感性协议**：附录 C 的"剔除不可读子集重算、报 Spearman ρ 与最大位次变化"——我们的 `stress` 分层就该这样报。
* **每图参数日志与场景映射**：本仓 `files.jsonl` 的 `ops` 字段已经等价；缺一个独立的 `scene_mapping` 汇总。
* **数据卡的 Out-of-Scope 段**：明确写"不得用于识别真实个人、不得把合成内容当事实记录"——我们的 README 隐私契约里没有这一段的"用途"版本。
* **Croissant 元数据与分卷 SHA256**：发布时照做。
* **模型推理配置与提示词的公开**（`model_inference/configs`、`prompts/`）：我们跑面板时要留同样的东西。

### 8.4 要避开的坑

* 不要用 LLM 一次性生成页面内容（我们没有；但 RESEARCH §5.3 提到的"日记句子 LLM 改写"要坚持"真值固定、只换说法"，并把改写前后的语义真值做等价断言）。
* 不要让标注依赖 LLM（我们是程序编译 + `readability` 核对，保持）。
* 不要每页只配一条采集链路而不报份额（我们的 `TIER_WEIGHTS`/`SCENE_WEIGHTS` 要在论文里连同真实语料的代理量一起报，degrade.md §3）。
* 不要在论文里攻击对手基准的标注质量（v1→v2 的教训；PAPER.md §0 已定"只报口径问题"）。
* 不要把"源可追溯"说成"零误差"——报自己的复核数字（文本层 39,887 行 0 丢失是现成的）。

## 10. OmniDocBench：真实性路线是怎么构造的

OmniDocBench（Ouyang 等，CVPR 2025，arXiv:2412.07626；上海 AI Lab / OpenDataLab）是 PureDocBench 要取代的对象，也是它的评测框架来源。
两者在**内容来源**上是反面（真实页 vs 生成页），在**标注格式与指标**上是同一套（PureDocBench 直接输出 OmniDocBench 格式、调用它的评测器）。

### 10.1 数据获取：先按视觉多样性采样，再按属性配平

| 步 | 做法 | 数字 | 出处 |
|---|---|---|---|
| 1 | 收集 PDF：Common Crawl、Google、百度搜索、内部数据 | 20 万+ 份 | 论文 §3.1 |
| 2 | 每页用 **ResNet-50** 抽视觉特征，**Faiss** 聚类 | 10 个聚类中心 | 论文 §3.1 |
| 3 | 从聚类中心附近采样视觉多样的页 | 6,000 页 | 论文 §3.1 |
| 4 | 标注员给每页打**页面属性**（文档类型、版式类型、语言），再按属性**配平** | 保留 981 页（v1.0） | 论文 §3.1 |
| 5 | v1.5 加 374 页（报纸/笔记从 72 dpi 提到 200 dpi）→ 1,355 页；v1.6 再加 296 页，"选更难的场景类别" → 1,651 页 | | GitHub README |

最终构成（v1.0）：9 种文档类型（学术论文、PPT 转 PDF、书籍、彩色教材、试卷、笔记、杂志、研报、报纸）；语言英文 290 / 中文 612 / 混排 79；
19 个区域类别、2 万+ 块级标注（文本段 15,979、图 989、表 428）、7 万+ 行级标注（含行内公式 4,009）、阅读顺序 1.6 万+。

### 10.2 属性体系：这是它真正可搬的东西

| 层级 | 属性 | 取值 |
|---|---|---|
| 页面（6 项） | 文档类型 | 9 类 |
| | 版式类型 | 单栏 / 双栏 / 三栏 / 混合 / 其它 |
| | 语言 | 英 / 简中 / 中英混 |
| | 水印 | 有 / 无 |
| | 模糊扫描 | 是 / 否 |
| | 彩色背景 | 是 / 否 |
| 表格块 | 方向、合并单元格、边框样式、语言、含公式、背景色、旋转 | |
| 文本块 | 语言、背景色、旋转 | |

榜单按这些属性分桶报分（"按文档类型"、"按版式"、"模糊 vs 清晰"）。这就是"配平"的目的：**每个桶里样本够多，才能单独报分**——它刻意扭曲了真实份额来换取每桶可测。

### 10.3 标注：模型预标 → 人工修正 → 专家质检

版式用微调的 LayoutLMv3 预标；文本 / 公式 / 表格用 PaddleOCR、UniMERNet、GPT-4o 预标；标注员逐块修正；三名研究者做专家质检（复杂公式与表格）。
PureDocBench v1 审计称其中 12.08% 的评分块有错（v2 撤回了这个数字，只留示例）。这是"转写真值"路线的固有成本：**真值是从页面上抄下来的，不是从源头编译出来的**。

### 10.4 分数饱和

v1.6 榜首 TeleOCR 96.91、OvisOCR2 96.47、PaddleOCR-VL-1.6 96.34——都在 96 以上；同一批模型在 PureDocBench 上最好 79.69，在其医疗域 Real 轨上最好 70.85。
三个数放一起说明的不是"PureDocBench 更难"，而是**分布不同**：OmniDocBench 的页是公开网络上能爬到的排版精良的 PDF，训练集里大概率见过同类；真实上传的健康档案（六成走 OCR、四分之三版式独一无二）离这两者都远。**我们的语料上分数会更低，这不是缺陷，要提前在论文里解释分布差异。**

### 10.5 对我们的适用边界

* 它的**采样思想**能搬：视觉聚类找家族 → 属性标注 → 配平 → 按桶报分。
* 它的**内容来源**不能搬：从搜索引擎爬医疗报告，爬到的是真实病人贴在网上的单子，不因为"公开"就可用；我们的结构来源只能是已授权的私有语料（627 份，法务口径待定，PAPER.md §11）与许可清楚的公开集（MedRepBench，仅限研究、且只用作外部锚点不进 spec）。
* 它的**标注路线**不能搬：转写真值贵、错、且没有语义层；我们必须走源编译（PureDocBench / WeVisDoc 路线，本仓已是）。

## 11. 融合设计：结构学 OmniDocBench、值学 mirobody-gen / Synthea、劣化学 PureDocBench

提出的融合是对的，而且本仓已经站在三分之二的位置上。把它写成三层分离的架构，每层说清"从谁那里学什么、本仓现状、要补什么"。

### 11.1 三层分离

| 层 | 学谁 | 学什么 | 本仓现状 | 要补的 |
|---|---|---|---|---|
| **S 结构层**（版式家族、页面属性、采集链路的**真实分布**） | OmniDocBench | 视觉聚类 → 属性标注 → 配平 → 按桶报分 | 符号级蒸馏：`analysis/*.json` → `spec/layout.json`（列组 20、参考值方言 64、标记 24、日期格式 19、构件 12、文档种类 21、单位位置 5）；机构过程复现指纹比例；`audit/fingerprint.py` 对账；图像聚合量 `numbers_images.json` | **视觉级家族**（符号指纹看不到的东西：无表格的叙述页、科室分栏框、页眉横幅、印章、App 截图外框）；**页面属性体系与配平**；**采集链路份额的实测**（degrade.md §6.6 明确写着没量） |
| **V 值层**（谁、什么时候、什么值） | mirobody-gen 队列引擎；Synthea/PySynthea 作病程与事件的接缝；ESL-Bench 用户作 Δ 实验的共用虚拟人 | 机理取值、恒等式、参考区间出处、纵向 RCV、诊断—值互证、黏性所见 | 已落地（PLAN §7.1–7.4；RESEARCH-2026-09-29 §1 决定暂不接 PySynthea 种子层，接缝留着） | 不变。这一层不从 OmniDocBench 或 PureDocBench 学任何东西——它们都没有值层 |
| **D 劣化层**（同一份内容以什么样子到达） | PureDocBench + WeVisDoc | 对齐视图、算子链、可见性规则、每图参数日志 | 24 场景、按 315 张真实图校准（degrade.md） | 真实手拍轨；场景份额由 S 层的属性标注给出，而不是照 PureDocBench 的 66 页样本量级 |

**关键性质**：三层正交之后，同一个生成器能出两种语料——`main` 按真实份额抽（聚合分数反映真实世界的混合），`balanced` 按属性配平抽（每桶 ≥ N 份，可以单独报分）。OmniDocBench 只能二选一（它选了配平），PureDocBench 也只能二选一（它按子类均匀）。**这是合成路线相对两者的一个实打实的优势，论文里要点明。**

### 11.2 S 层的具体做法（OmniDocBench 流程搬到私有语料上）

输入：参考集（不随仓库分发）的 315 张图像 + 543 份 PDF 的逐页栅格化（约 1,000+ 页）。全部在有语料的机器上做，**中间产物一律不出机**。

| 步 | 做法 | 产物 | 出闸规则 |
|---|---|---|---|
| S1 | 每页抽视觉嵌入（ResNet-50 与 OmniDocBench 同款即可；DINOv2 更适合版式，二者都可试） | `.cache/page_embeddings.npy` | **不出机**。嵌入是成员判定预言机，与 `.cache/corpus_ngrams.npy` 同等对待（README 隐私契约） |
| S2 | k-means（Faiss 或 sklearn），K 用轮廓系数在 8–24 里选；每簇出一张接触表（缩略图拼图）供人看 | `.cache/clusters/` | 不出机 |
| S3 | 人对**簇**打属性（不是逐页）：文档种类、版式类型（单表 / 多表 / 键值对 / 叙述 / 混合）、表格边框样式、页眉横幅、印章/签名、栏数、科室分栏、叙述占比、语言混排、单位位置、参考值方言、横竖版、**采集链路**（扫描 / 手拍 / 复印 / 截图 / App 增强）、模糊、彩色背景、水印、旋转 | `analysis/page_attributes.csv`（逐页，不出机） | 逐页属性表含文件名，不出机 |
| S4 | 聚合：每个家族的份额、属性边缘分布与联合分布（只保留 n≥3 的组合）；家族 → 机构模板的映射由人写成虚构机构的 spec | `spec/layout_families.json`（source: format-token） | **过闸**：只有计数与类别值；n<3 的家族合并或丢弃（一个家族 = 一家机构的模板，PLAN §4.2 的 n≥3 规则同样适用） |
| S5 | 生成器：机构过程按家族份额抽机构，每家机构的粘性版式从其家族的属性联合分布里抽；`files.SCENE_WEIGHTS` / `TIER_WEIGHTS` 改为从 S3 的采集链路计数算出 | `generator/files.py`、`generator/layout.py` | — |
| S6 | 覆盖测试（PLAN §3.6.4 的视觉版）：合成页用**同一个**嵌入模型编码，检查每个真实簇中心附近都有合成页（最近距离 ≤ 阈值），并比较家族份额 | `audit/fidelity.py --visual` | 报告只含距离分位数与份额 |
| S7 | 评分器按桶报分：家族 × 层级 × 场景 × 陷阱类 | `harness/score.py --by family,tier,scene,hazard` | — |

工作量估计：S1–S2 一天；S3 按簇标注两到三天（1,000 页逐页标要一周以上，按簇标是 OmniDocBench 这套流程的省力之处）；S4–S5 两到三天；S6–S7 一天。

### 11.3 融合后的闭环长什么样

```
真实语料（不出机）──S1–S4──▶ spec/layout_families.json（家族份额、属性分布、采集链路份额）
                                        │
ESL-Bench 用户 / 队列引擎 ──V──▶ 真值（就诊、读数、主诉、所见、设备、基因、日记）
                                        │
                              渲染：家族模板 × 值 ──▶ T0 文本层（印刷真值 + 语义真值 + 块真值 + 陷阱名）
                                        │
                              D：按采集链路份额劣化 ──▶ T2/T3/T4/T6 + 对齐视图 + 真实手拍轨
                                        │
                              mirobody 产线（提取 → 解析 → 编码 → agent）
                                        │
                              评分：按家族/场景/陷阱分桶；对照对给配对差；语义层判弃权
                                        │
                              失败簇 ──▶ 回灌：该家族/场景/陷阱在下一批里加权（WeVisDoc 探针思想）
```

"从而进一步获取 raw data 的样式"在这张图里的位置：S 层给**版式的样式**，D 层给**采集的样式**，两者都从真实分布校准；V 层保证内容是合理的但不是真的。三者的输出就是"样子像真实上传、内容可断言、隐私结构上安全"的 raw data。

### 11.4 三点提醒

1. **不要把 MedRepBench 同时当校准源和锚点**。S 层的分布只从私有语料来；MedRepBench 只做 E2 的外部锚点。两边的属性分布可以并排报，让读者看到差距。
2. **家族的"模板"是人重画的，不是从真实页抠的**。视觉聚类告诉我们"有这么一类"，机构模板由人按属性写成虚构机构的 spec；这与 §4.2 "模板化而不是实例化"一致。
3. **配平后的 `balanced` 语料不进主榜**，主榜报 `main`（真实份额）；两者都由同一 seed 生成，方法学上与 `stress` 分层同样处理。

## 12. Synthetic Hospital 精读：另一条"真值先于叙事"的路线

### 12.1 档案

| 项 | 内容 |
|---|---|
| 标题 | *Synthetic Hospital: An Open, Verifiable, Physician-Validated Longitudinal EHR Benchmark* |
| 作者 | Christine Park、Valerie Chen、Tim Dettmers，卡内基梅隆大学 |
| 版本 | arXiv:2609.30027 v1，2026-09-24，29 页；代码与数据 `github.com/sparkcpark/synthetic_hospital` |
| 规模 | 1,268 名纵向患者、5,602 次就诊、12,014 道题；public 200 患者 / train 800 / held-out 268（held-out 标签只在评分器里） |
| 要解决的两个障碍 | 真实 EHR 不能开放共享；真实病历只记录"医生写了什么"，模型答错与病历本来就缺分不开 |
| 核心原则 | **标签在叙事生成之前由本体图确定性导出，渲染用的 LLM 碰不到真值**（图 1 的原话：labels are derived before narrative generation, preserving provenance and independence from the rendering language model） |

### 12.2 五阶段流水线

| 阶段 | 做法 | 谁做 | 数字 |
|---|---|---|---|
| (1) 知识摄入 | USMLE 式题库 + 闪卡与参考文档，规则解析成统一结构，保留元数据与出处；题变成候选就诊，闪卡变成支持知识 | 程序 | 7,003 道题；53,999 张事实卡 |
| (2) 本体落地与知识图谱 | Kimi 2.5 从每题抽主诊断、鉴别诊断、次要诊断与分型所见（9 型：症状/体征/化验/生命体征/影像/操作结果/病史/用药/人口学；4 级相关性 key/supporting/background/distractor）。**LLM 给的码只当候选**：ICD-10-CM 用确定性级联（表查 83.2% → 名匹配 0.2% → 模糊 ≥0.70 4.3% → 标记未验证 7.3% → 未编码 5.0%）；SNOMED 四道（精确 → ICD 映射表 → 模糊 0.95/0.90 → SapBERT 0.70/0.65）；**LOINC 不用 LLM**，剥值、剥单位、剥修饰后匹配。第二遍 LLM 给诊断—所见边分 6 型；第三遍链接事实卡，只能解析到已有节点、不造新概念；每题按 18 个 EHR 段切分，原文照抄 | LLM 提候选，程序判定 | 诊断 9,623（ICD 75.9% / SNOMED 88.0%），所见 36,620（SNOMED 97.5%），化验所见 3,488（**LOINC 仅 28.9%**），典型边 52,082 |
| (3) 纵向患者拼装 | **先聚类后叙事**：同性别、同年龄桶（容差 2/5/7/10 岁）、社会史不矛盾为"相容"；共享正确或次要诊断为"相连"（错误选项不算）。受约束贪心：簇内两两相容、相连图连通；簇大小按急慢性定 3/5/8；每题只进一个患者；无随机、无 LLM、秒级。然后 Kimi 2.5 生成画像（12 个固定键，不得与原文矛盾）、时间线（7 种就诊类型、月份、≤10 年、程序校验）、非首次就诊的 HPI 改写（保留全部临床细节、不加所见、≤150% 长度）。病历按段确定性拼装：既往史前缀早先诊断的问题清单，家庭用药追加；**逐行记录来源段与是否修改**；医生审阅 | 程序聚类，LLM 叙事 | 1,268 患者 / 5,602 就诊（1,401 题落单）；簇大小 2 次 350、3 次 355、8 次 331…；门诊 3,079、急诊 1,755、住院 383、ICU 296 |
| (4) 基准构造 | 除影像指征外，标签是图的确定性函数：**患者诊断**（正确诊断集，ICD 三位类目匹配，严重度权重 3/2/1，指标为加权召回与精确率的调和均值；图外诊断"不奖不罚"）；**证据检索**（段落按所见相关性 × 边强度评 0–3）；**总结**（key 所见 ≤20 条，缩写与否定感知的匹配）；**专科条件总结**（诊断→专科表；所见分 primary/relevant/neutral/excluded；头分 = 关键召回与 1−泄漏 的调和均值；含"该专科无相关问题"的**弃权题**）；**影像指征**（唯一 LLM 写的参考：按图固定的诊断写终端医嘱与参考问题，按概念 F1 评） | 程序（一项 LLM） | 12,014 题；每次 LLM 调用按输入 SHA-256 缓存并记日志 |
| (5) 域真实模拟 | FHIR R4、基于角色的访问控制、Epic 式工作流、13 个工具的函数调用接口；每个暴露元素带溯源链 | 程序 | agent 评测 40 步预算 |

### 12.3 验证与结果

**记录层真实感（§4.1）**：把 5 名 MIMIC-IV 真实患者用**规则**转成同一格式（18 段、日期平移到 2020–2024、假名、化验展开为一行一项带全名单位参考范围、缩写展开），与 5 名按科室/性别/年龄/长度配对的合成患者混在一起，10 名执业医生各判 10 份、顺序随机：准确率 **53%**（95% CI 43–63，p = 0.62），敏感 52% / 特异 54%，Fleiss κ = −0.05（没有共同线索），无人显著高于随机，每份合成病历都至少被一名医生判成真；自信 100% 的判断也只有 70% 准。作者的结论："真实感来自纵向临床表示本身，不来自复现某家机构的文档风格"。

**真值有效性（§4.2）**：医生预注册 119 对必需的诊断关系，图恢复 111（93%）：96 来自 SNOMED 关系、共享解剖部位或共享所见，15 来自医生手工加边；8 对承认缺口（两病无共享所见，如妊娠剧吐—Wernicke 脑病），**没有为此调低阈值**。假阳性关系未量化。

**模型结果（§5，表 3）**：10 个模型；患者诊断最好 0.73（Kimi 2.5-thinking）、GPT 5.3 0.70，七名医生均值 0.66（区间 0.21–0.89）；总结与影像指征 ≈ 0.5；检索 P@5 全部 >0.74；**幻觉率近零，主要失败是遗漏**（总结遗漏 45–62%，专科总结 47–79%）；前沿模型之间高度压缩（前四相差 0.06）。Prompt 策略先在 3 个模型上消融再按任务锁定（不同任务最优策略不同）。

**Agent 评测（§5.3，表 4）**：证据已给全时，多轮循环在九组模型—任务上全部负效应（−0.07 到 −0.24），自检索几乎补不回来；只有患者诊断（证据跨就诊分布）自检索 agent 胜过单轮 LLM（+0.14 到 +0.34）；失败会话平均耗 145k 输入 token，成功的 60k。

**生成器鲁棒性（附录 C.2）**：同一图状态换 GPT 5.3 重渲染 100 名患者，四个模型的主指标变化 |Δ| ≤ 0.05（检索除外，全体同降），Kimi 没有"主场优势"，排名 Spearman ρ ≥ 0.80。**这个实验设计我们要照抄**（§14 阶段 6.3）。

**分布特征（附录 H）**：与题库同分布（JSD 0.029），与 Synthea 人群队列明显不同（JSD 0.326；Synthea 56.8% 是 Z 码，它只有 9.3%）；十对经典共病 OR 全部 >4。作者明确：不是人群校准，不该用于流行病学推断或替代训练数据。

**局限（作者自述）**：医生样本小；教育题库导致罕见与非典型表现不足；**没有模拟缺失、矛盾与文档错误**；agent 只测三模型三条件；图外诊断不奖不罚导致真值可验证但不穷尽。

### 12.4 与本仓的对照

| 维度 | Synthetic Hospital | mirobody-gen |
|---|---|---|
| 场景 | 医院病历（急诊/住院/ICU 为主），诊断推理 | 个人健康档案（体检、慢病随访、居家设备），标准化与纵向管理 |
| 值与内容来源 | 教育题库里的病例，值是题里写的 | 机理模型 + 公开参考区间 + 生物学变异 + 恒等式 |
| 化验数据 | 3,488 条所见，LOINC 28.9%，无纵向轨迹，无参考范围 | 18,838 行读数，98 项指标 91% 可解析（循环性已注明），纵向 RCV，65 种参考值方言 |
| 真值原则 | 标签先于叙事，独立于渲染 LLM | **同**：语义真值先于渲染；印刷真值由渲染器写、`audit/readability.py` 核对 |
| 文档与图像 | 无（结构化 + API） | 726 份文件，52% 走 OCR 路径，24 个劣化场景 |
| 真实感证据 | 记录层：医生盲判 53% | 分布层：E1 指纹与方言对账；**缺记录层盲评** |
| 真值有效性 | 119 对医生预注册关系，93% 恢复 | 12 条恒等式 + 诊断—值互证；缺医生预注册式的外部对照 |
| 拆分与封存 | public / train / held-out，held-out 标签只在评分器 | dev seed 与 sealed seed（PLAN §9.6 提过，未落地） |
| 生成器鲁棒性 | 换 LLM 重渲染，排名不变 | 未做；若做"日记 LLM 改写"则必需 |
| 缺失、矛盾、错误 | 明确不模拟 | **这是我们的核心**：陷阱、必须弃权、劣化、跨文件重复 |
| 评分 | chart-neutral：图外诊断不奖不罚 | `readable=False` 移出召回分母、必须弃权 |
| 可训练性 | train 拆分 7,619 题 × k 次 rollout，图给确定性奖励 | 行级真值天然是可验证奖励；未作为卖点写 |

**一句话**：它与 ESL-Bench 同赛道（纵向合成 + 可验证真值），比 ESL-Bench 多了本体落地、医生验证与 EHR 模拟，少了设备流与事件驱动的指标级联；它与我们不在同一层——它停在"结构化真值 + 叙事文本"，我们从那里开始往文件、图像、脏数据走。相关工作里把它放在"值层"一栏，正面对比三点：真值先于渲染（同）、记录层盲评（我们要补）、缺失与错误的建模（我们有它没有）。

## 13. 整体流程复审：十三个问题

对照本仓当前的流水线（`scripts/build_* → generator.build → files.render_corpus → audit.* → harness.*`）与 §11 的融合设计，逐条审。严重度：A 影响论文成立，B 影响可信度，C 工程债。

| # | 问题 | 严重度 | 后果 | 处理（进 v2 的哪一步） |
|---|---|---|---|---|
| 1 | **真实感只有分布层证据**，没有记录层的人工盲评；审稿人会拿 Synthetic Hospital 的 53% 来比 | A | "像真的"这句话没有直接证据 | 阶段 6.2 盲评 |
| 2 | **回灌会毁掉基准**：失败簇加权回生成器、mirobody 再修，几轮之后语料变成调参目标（mirobody `eval/README.md` 已担心过） | A | 分数不再反映泛化 | 阶段 4.2 双种子：dev seed 可回灌，sealed seed 冻结、真值只在评分器里 |
| 3 | **评分只覆盖检验行**：主诉/日记、设备、基因、键值对、总检、跨文件去重都有真值但没有评分面（RESEARCH §7 第 7 条） | A | 多源同源是我们的主张，却没数字 | 阶段 5 多评分面 |
| 4 | **结构层有两套真值来源**：符号 spec（`layout.json`）与拟加的视觉家族（`layout_families.json`），若各自采样会互相矛盾、双重计数 | B | 保真度数字对不上、机构模板不自洽 | 阶段 2.1：家族 → 属性 → 条件采样符号 spec，单一入口 |
| 5 | **视觉家族的属性标注是主观的**，单人标没有一致性数字 | B | OmniDocBench 有标注员 + 专家质检，我们没有 | 阶段 0.4 双标 + κ，schema 版本化 |
| 6 | **没有真实手拍轨**，也没有决定它的真值与质量标志怎么记 | B | PureDocBench 5.63% 不可读的教训会重演 | 阶段 3.4 事前可读性筛 + quality flag |
| 7 | **多页文件一页一张照片**未做（degrade.md §6.1），而这是体检报告书上传的主流形态 | B | 语料缺一整类到达形态；mirobody 的多文件合并测不到 | 阶段 3.3，真值按页拆、共用 doc_id |
| 8 | **跨文件重复读数没有真值链接**（同一值印在化验单与报告书、AST 印两次、"上次结果"列） | B | 去重能力测不到，纵向合并的分数无法归因 | 阶段 2.3 `duplicate_of` |
| 9 | **图像层的 GT 错误预算未定义**：`readability --ocr` 只报告不判定，没有人工抽检协议 | B | 我们批评 OmniDocBench 12%、PureDocBench 2.5%，自己却没数 | 阶段 3 闸门 G3：每场景抽 n 张人工核对，报错误率 |
| 10 | **生成器鲁棒性未测**：同一真值换家族 / 换渲染器 / 换改写模型，排名是否稳定 | B | 若做日记 LLM 改写，审稿人必问"是否偏向该模型" | 阶段 6.3 |
| 11 | **值层案例组合的出处没有对账**：`cohort.json` 的患病率是手写的，没有像 Synthetic Hospital 附录 H 那样报与先验来源的 JSD | B | "合理"只有恒等式证据，没有人群证据 | 阶段 1.4 |
| 12 | **spec 的语料快照没有版本锚**：627 份文档的快照哈希与蒸馏脚本版本没记进 `numbers.json` | C | 换一批语料重蒸馏后数字漂移无从追溯 | 阶段 0.1 |
| 13 | **外部系统跑不动我们的语料**：评分要 import 本仓，MedRepBench 视图只覆盖检验行 | C | 采用路径断了（§5.5 的结论） | 阶段 5.8 独立评分 CLI + PureDocBench 格式导出 |

另有两条不改的决定，写明理由：

* **不接 PySynthea 作种子层**（RESEARCH §1 的决定不变）：它的主诉是诊断名、只有 us locale、精度未修；接缝保留。
* **不用 LLM 生成页面内容**（§8.4）：Synthetic Hospital 的经验恰好支持——它把 LLM 限制在叙事，真值全部程序导出；我们比它更进一步，连叙事也是模板加槽位。

  G3 [新] 图像层 GT 错误预算：每场景抽 n 张人工核对印刷真值可见，报错误率；--ocr 只作参考；severe → stress

阶段 4 语料装配与封存
  4.1 [改] 三个分层：main（真实份额）/ balanced（配平，每桶 ≥ N）/ stress（severe + 超 p95 陷阱）
  4.2 [新] 双种子：dev seed（公开、可回灌）与 sealed seed（真值只随评分器发布；家族/场景/陷阱配比冻结）
  4.3 [新] 版本化与元数据：GT 版本别名、changed_cases、Croissant、数据卡 Out-of-Scope（学 PureDocBench）
  G4 [有] audit.privacy 扫 out/：回放、PII、白名单、合成编号校验

阶段 5 评测：一份报告、多个评分面
  5.1 [有] 抽取面：印刷层五字段，官方口径（MedRepBench V0）+ 对齐口径
  5.2 [改] 标准化面：语义层 LOINC / UCUM / 日期 / 必须弃权（score.py 已留接口）
  5.3 [新] 主诉与日记面（ICPC-3 三态）、设备面（crosswalk 命中）、基因面（called / unresolved / no_call）
  5.4 [新] 纵向面：跨文件去重、同源一致性（体重秤 vs 体检体重、血压计 vs 门诊血压）
  5.5 [新] agent 面：ESL-Bench 原查询，Δ = 结构化入库 − 文件入库，拆抽取 / 术语 / 推理三段
  5.6 [改] 分桶报告：家族 × 层级 × 场景 × 陷阱类；对照对配对差；stress 单列
  5.7 [新] 外部锚点：MedRepBench（真实）、PureDocBench 06_medical（合成第三方）排序一致性
  5.8 [新] 独立评分 CLI（不 import 生成器）+ PureDocBench / MedRepBench 格式导出
  G5 [改] 评测有效性：官方与对齐口径并报；GT 错误预算（阶段 3）随分数一起报

阶段 6 效度证据（论文的第 5、6 节）
  6.1 [有] 分布层：E1 fidelity + [新] 视觉覆盖
  6.2 [新] 记录层盲评：10 评审 × 10 份（5 真实 5 合成，按文档类型/语言/长度配对），报准确率、CI、κ；真实件用私有语料时评审须有授权，或用 MedRepBench 公开图像做外部版
  6.3 [新] 生成器鲁棒性：同一真值换家族 / 换渲染器 /（若有 LLM 改写）换模型重渲染，排名 Spearman ρ
  6.4 [新] 敏感性：剔除不可读与 stress 重算（PureDocBench 附录 C 式）

阶段 7 回灌（只作用于 dev seed）
  7.1 失败簇 = 分桶分数最低的（家族 / 场景 / 陷阱）组合 → 下一批 dev 语料加权（WeVisDoc 探针思想）
  7.2 mirobody 侧修复 → 重跑阶段 5；发布数字一律取 sealed seed
